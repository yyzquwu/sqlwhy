## Case notes

- **a1** Issue #120 reported that an invoice ID shared by several QuickBooks sources picked up other sources' payment IDs. The merged diff adds source_relation to the invoice_pay join and carries it into downstream joins. Isolates invoice_pay with synthetic inputs, adds a unique invoice row ID for tracing, and omits the invoice estimate and downstream merges. The excerpt comes from a dbt model that requires rendering. [Source](https://github.com/fivetran/dbt_quickbooks/blob/505a2f48c0f07f10d6ef0ef516b84e1a7800c48f/models/intermediate/int_quickbooks__invoice_join.sql#L51-L62) · [Fixture](cases/a1.json)
- **a2** The v0.12.1 changelog and merged diff document an inner-to-left join change because the account lookup could be empty and remove transactions. This case uses the bill payment model among the five changed models. Supplies synthetic inputs to bill_payment_join and selects only its transaction ID and account ID. The dbt staging and double-entry output steps are omitted. [Source](https://github.com/fivetran/dbt_quickbooks/blob/74da53b53cc1acf0cd29275744263dd4757ce589/models/double_entry_transactions/int_quickbooks__bill_payment_double_entry.sql#L38-L55) · [Fixture](cases/a2.json)
- **a3** The merged diff changes the abandoned-checkout discount model to sum shipping prices by checkout_id and source_relation before joining. Previously each shipping line could replicate the same discount contribution before the report grouped by discount code and type. Replays the changed join at the pre-aggregation grain and materializes the new shipping rollup in fixture setup. The checkout details join and final report aggregation are omitted, so counts measure contributions to the aggregate. [Source](https://github.com/fivetran/dbt_shopify/blob/304c7ee7f4c1d229981b491c9bf2b60a7411f73b/models/intermediate/int_shopify__discounts__abandoned_checkouts.sql#L27-L46) · [Fixture](cases/a3.json)
- **a4** The merged Superset dataset patch replaces a course-run lookup whose platform uses display names with a dimensional lookup whose platform uses codes. The PR reports that the mismatched inner join caused the chart to return no rows. The saved before SQL is the complete YAML block with standard YAML indentation removed. The replay adds the id projection. Its fixed query references a fixture view implementing the dimensional title lookup from the merged SQL. The original schema and table names resolve to synthetic DuckDB tables. [Source](https://github.com/mitodl/ol-data-platform/blob/3c978e9a6cdc9d3253a68bca3c06f17a6b9193c3/src/ol_superset/assets/datasets/Trino/discussion_detail_report_ec0fc17c-ebca-44ae-94ae-2072da856d24.yaml#L155-L169) · [Fixture](cases/a4.json)
- **a5** The merged calendar-resolution model changed the status-history filter to admit both solved and closed events, then uses a closed timestamp when a ticket has no solved timestamp. Closed-only histories previously supplied no row to the resolution-time aggregate. Replaces the dbt relation reference with a fixture table and replays only the input filter. The count measures qualifying history rows. The later resolution fallback and final ticket report are outside this replay. [Source](https://github.com/fivetran/dbt_zendesk/blob/1ad0a86859f8c589889e7a736130eadb04a4d6d2/models/resolution_times/int_zendesk__ticket_resolution_times_calendar.sql#L1-L7) · [Fixture](cases/a5.json)
- **b1** The issue supplies a compact executable SQL reproduction of the generated findTags query. The OR filter lost matching names without aliases because the inner join removed those tags before either predicate ran. The merged fix converts joins in both OR branches to left joins and adds regression coverage. The literal is the issue reporter's runnable reproduction. The local replay removes DISTINCT and uses fixtures with at most one alias per tag, so row multiplicity from DISTINCT is irrelevant. The logged application query also had bound parameters and SQLite collation-specific sorting. [Source](https://github.com/stashapp/stash/commit/fc0b2a5d9647110ab274c3c49ad3871124fe42c4.patch) · [Reporter’s query](https://github.com/stashapp/stash/issues/6914) · [Fixture](cases/b1.json)
- **b2** The maps sources API lost otherwise eligible sources whose scale was NULL or absent from its hard-coded sort lookup. The merged patch changes only the scale lookup join from inner to left. The replay materializes the four original VALUES entries as a DuckDB table. It uses the all-sources path with the published eligibility filters, synthetic non-NULL geometry markers, and only the source ID projection. It omits formatting, ordering and the optional sample limit. [Source](https://github.com/UW-Macrostrat/macrostrat-api/commit/1fb593e5cec0ba5cee29f86e34cb5892aff179f0.patch) · [Fixture](cases/b2.json)
- **b3** The SQLAlchemy-backed semi_join selected only left columns from an inner join, so duplicate keys on the right duplicated left rows. The fix uses correlated EXISTS and includes a regression test with two right records for one key. The replay translates the SQLAlchemy construction to an inner join and the upstream correlated EXISTS, keeping the duplicate-key case from the regression test. It replaces ORM-generated aliases, selects a stable synthetic row ID, and omits unused dataframe columns. [Source](https://github.com/machow/siuba/commit/e5b1394bfa108c41f48d194804c8d4d078f22807.patch) · [Fixture](cases/b3.json)
- **b4** Product::sqlStock applied stock attribute and shop restrictions in WHERE when called with a query builder. The fix put the restrictions into the LEFT JOIN condition in the stock SQL used by the cart and new-product queries. The replay keeps the stock join and the zero-attribute branch, using one synthetic shop. It omits the separate shop and product filters, other product joins, table prefixes, and projections unrelated to the row loss. [Source](https://github.com/PrestaShop/PrestaShop/commit/4de6cc643f0b9219d91c9db3bc2bddb5bdfd5912.patch) · [Fixture](cases/b4.json)
- **b5** Active milestone progress joined issues on milestone_id alone, although milestone IDs can repeat across projects. The fix adds project_id equality so the weighted calculation uses issues from the active project only. The replay fixes the active project in a WHERE filter and projects the milestone ID to count contributing rows before aggregation. It drops the user-settings and issue-weight lookups and uses synthetic issues with the same milestone ID in two projects. The complete upstream query also has GROUP BY and three joins. sqlwhy rejects GROUP BY, and DuckDB additionally needs the selected title in GROUP BY. [Source](https://github.com/chylex/Lightning-Tracker/commit/2f5d58edc87b736c12b9c6963eb347ab7b0d813a.patch) · [Fixture](cases/b5.json)
